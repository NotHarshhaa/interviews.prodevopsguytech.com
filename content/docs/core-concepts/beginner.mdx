# Beginner Level

This section covers fundamental concepts of DevOps, including basic principles, practices, and essential tools.

<Steps>
<Step>
**What is DevOps?**

DevOps is a set of practices — and equally a culture — that combines software development (Dev) and IT operations (Ops) so teams can deliver software **faster, more reliably, and with shared ownership**.

The two halves of the definition:

- **Practices** — CI/CD, infrastructure as code, monitoring, automated testing
- **Culture** — developers and operations share goals, tools, and responsibility ("you build it, you run it") instead of throwing work over a wall

A precise one-liner for interviews: *"DevOps removes the gap between writing software and running software, using automation and shared ownership."*
</Step>

<Step>
**What are the main goals of DevOps?**

- **Faster delivery** — small changes shipped frequently instead of big releases shipped rarely
- **Reliability** — deployments become routine and reversible, not high-stakes events
- **Collaboration** — dev and ops share metrics, tools, and accountability for the same outcome
- **Automation of repetition** — builds, tests, provisioning, and deployments run without manual steps
- **Continuous feedback** — monitoring and post-incident learning feed straight back into development

The underlying theme: shorten and strengthen the loop between "idea" and "running safely in production, observed".
</Step>

<Step>
**What are the key components of a DevOps practice?**

- **CI/CD** — automated build, test, and deployment pipelines (the delivery backbone)
- **Infrastructure as Code** — infrastructure defined in versioned files, not console clicks
- **Monitoring & observability** — logs, metrics, traces to know what's happening in production
- **Configuration management** — keeping environments consistent automatically
- **Collaboration practices** — shared repos, PR reviews, blameless post-incident reviews

Also worth naming: automated testing as the quality gate, and security woven in (DevSecOps) rather than bolted on at the end.
</Step>

<Step>
**How does DevOps differ from traditional IT operations?**

| Aspect | Traditional (siloed) | DevOps |
|---------|---------------------|--------|
| **Team structure** | Devs write code, "throw it over the wall" to Ops | Shared ownership, cross-functional teams |
| **Releases** | Infrequent, big-bang, manual | Frequent, small, automated |
| **Change process** | Tickets, change boards, long lead times | Pipelines, review gates, minutes-to-hours |
| **Feedback** | Users report outages | Monitoring detects problems first |
| **Failure culture** | Blame the person | Blameless post-mortems, fix the process |

The root difference to articulate: traditional ops optimizes for *change avoidance* (stability through not touching things); DevOps optimizes for *safe, fast change* (stability through small reversible steps).
</Step>

<Step>
**What is Continuous Integration (CI)?**

CI is the practice of merging small code changes into a shared mainline frequently (at least daily), where each merge automatically builds the code and runs tests:

```
push → build → unit tests → lint/scan → pass = mergeable, fail = fix now
```

The value: integration problems surface within minutes of the change that caused them — when the cause is obvious and the fix is small — instead of festering for weeks until a painful release-merge. Two rules make CI real: the main branch is kept green, and the pipeline is fast enough that developers trust it.
</Step>

<Step>
**What is Continuous Deployment/Delivery (CD)?**

- **Continuous Delivery** — every change is automatically built, tested, and *staged ready for release*; a human approves the production push
- **Continuous Deployment** — every change that passes the pipeline goes **all the way to production automatically**

Everything up to production is identical in both — the difference is only the last human gate. Teams choose delivery when releases need business/compliance sign-off, and deployment when their tests, monitoring, and rollback safety nets are strong enough to trust fully.
</Step>

<Step>
**What is Infrastructure as Code (IaC)?**

IaC means defining infrastructure — servers, networks, load balancers, databases — in **declarative code files** instead of provisioning manually:

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0abc123"
  instance_type = "t3.medium"
}
```

What it changes: infrastructure gets version control (review every change), reproducibility (identical environments from the same code), drift detection (console changes become visible), and one-click rollback. Tools: Terraform (multi-cloud), CloudFormation (AWS), Ansible (configuration). Deep dive in the [Infrastructure as Code section](/docs/infrastructure-as-code/beginner).
</Step>

<Step>
**What is version control, and why is it critical in DevOps?**

Version control (Git) tracks every change to code and configuration — who changed what, when, and why — enabling collaboration, review, and rollback.

In DevOps it's bigger than "code backup": *everything* lives in Git — application code, pipeline definitions, infrastructure code, docs — which makes Git the single source of truth for the whole system. Pull requests gate quality (review + green pipeline), history enables audit and blameless forensics, and `git revert` is often the fastest rollback in production.
</Step>

<Step>
**What are some popular DevOps tools by category?**

- **CI/CD** — Jenkins, GitHub Actions, GitLab CI, Azure DevOps, CircleCI
- **IaC** — Terraform, CloudFormation, Pulumi
- **Configuration management** — Ansible, Chef, Puppet
- **Containers/orchestration** — Docker, Kubernetes, Helm
- **Monitoring/observability** — Prometheus + Grafana, ELK/OpenSearch, Datadog
- **Secrets** — HashiCorp Vault, AWS Secrets Manager

The interview tip: knowing *one tool per category deeply* beats reciting every tool superficially — interviewers follow up with "why that one?" and "how did you use it?"
</Step>

<Step>
**What is a DevOps pipeline?**

A pipeline is the automated workflow that carries a code change from commit to production:

```
commit → build → test → package artifact → deploy → verify/monitor
```

Each stage is a gate: failures stop the change right there. Pipelines encode your delivery process as code — reviewed, repeatable, and identical for every change — which is what makes frequent releases safe. "Pipeline" is the same word for GitHub Actions workflows, Jenkinsfiles, and GitLab CI configs; the concepts transfer.
</Step>

<Step>
**What is containerization?**

Containerization packages an application with its runtime and dependencies into an isolated, portable unit that runs identically on any machine — Docker being the standard tool.

Compared to VMs, containers share the host kernel: they're lightweight (MBs), start in seconds, and are dense on shared hosts. For DevOps the impact is foundational: the container image becomes the **immutable deployable artifact** — built once by CI, promoted unchanged through every environment — which eliminates "works on my machine" and enables orchestration (Kubernetes). Deep dive in the [Containers section](/docs/containers/beginner).
</Step>

<Step>
**What are microservices?**

Microservices split an application into small, independently deployable services, each owning its own logic and data, communicating over APIs:

- **Why teams adopt them** — independent deploys (ship one service without redeploying everything), per-service scaling, team autonomy, blast-radius isolation
- **The trade-off to acknowledge** — distributed-systems complexity: network failures between services, data consistency, harder debugging

The balanced beginner answer: microservices are a scaling and organization strategy, not a default — a well-modularized monolith is often the right starting point, with services extracted where independence genuinely pays.
</Step>

<Step>
**What is the difference between monolithic and microservices architecture?**

- **Monolith** — one codebase, one deployable unit, one database. Simple to develop, test, and operate early; scales as a whole; one defect can take down everything
- **Microservices** — many small services, separate deployables, separate data. Independent scaling and releases, team autonomy — at the cost of network complexity and operational overhead

The decision framing interviewers respect: start with a monolith until team size, scaling needs, or release cadence create real pain — then extract services along meaningful boundaries. The failure mode to avoid: "distributed monolith" — microservices that can only be deployed all together, with all the complexity and none of the benefits.
</Step>

<Step>
**What is shift-left testing?**

Shift-left moves testing (and security) **earlier** in the lifecycle — as close to the moment of writing code as possible:

```
traditional:  build → test → secure → release
shift-left:   [test + secure] → build → [test + secure] → release
```

Practically: unit tests on every commit, linters and secret scanners pre-commit, dependency and image scans in CI. The economic argument to make: a defect caught at commit costs minutes of developer time; the same defect in production costs an incident and customers' trust.
</Step>

<Step>
**What is observability in DevOps?**

Observability is the ability to understand a system's internal state from its outputs — asking new questions of production without shipping new code. The three pillars:

- **Metrics** — numeric time series (latency, error rate, saturation) for *what* is wrong
- **Logs** — detailed event records for *why* it went wrong
- **Traces** — a request's journey across services for *where* in the chain it went wrong

Observability goes beyond traditional monitoring (which answers predetermined questions like "is CPU high?") by supporting *arbitrary* questions about novel failures — the defining requirement of distributed systems. Deep dive in the [Monitoring & Logging section](/docs/monitoring-logging/beginner).
</Step>

<Step>
**What is a rollback strategy?**

A rollback strategy is the pre-planned way to return to the last known-good state when a release misbehaves:

- **Application** — redeploy the previous versioned artifact (never rebuild "the old version")
- **Traffic-level** — blue-green switch or canary weight shift back to the healthy version
- **Feature-level** — feature flags turn off the misbehaving feature without any redeploy — usually the fastest remedy
- **Database** — the constraint that shapes everything: schema changes must be backward-compatible, since data doesn't roll back like code

The interview point: every deployment must ship with a *tested* rollback path — and knowing your rollback time is part of knowing your release risk.
</Step>

<Step>
**What does a DevOps engineer actually do?**

A DevOps engineer builds and maintains the automated path from code to production:

- **Build & run CI/CD pipelines** — the delivery backbone every team relies on
- **Infrastructure as code** — provision and manage cloud resources reproducibly
- **Containers & orchestration** — package apps and run them on platforms like Kubernetes
- **Monitoring & observability** — dashboards, alerts, and participation in incident response
- **Security & reliability practices** — shift-left scanning, capacity, backups, DR

The framing to give: less "operations person who codes" and more "engineer who makes the whole delivery system work" — enabling development teams to ship safely and frequently themselves.
</Step>

<Step>
**What are feature flags?**

Feature flags decouple *deploying* code from *releasing* a feature: the code ships to production dark, and a flag turns it on for chosen users without any new deployment:

```
deploy v2.3 (flag off) → enable for 10% of users → watch metrics → 100%
```

Uses: gradual rollouts, instant kill switches (faster than rollback), A/B testing, and testing in production safely. The caveat that shows understanding: flags are technical debt — every active flag is a code path to test — so they need owners and expiry dates.
</Step>

<Step>
**What is a blue-green deployment?**

Blue-green runs two identical production environments: **blue** is live, **green** receives the new version and is tested privately, then traffic switches atomically:

```
users → LB → blue (v1.4)     --switch-->     users → LB → green (v1.5)
```

Strengths: near-instant rollback (switch back), full-environment verification before real traffic. Trade-offs: double infrastructure during the release, and stateful pieces (databases with schema changes) don't switch back as cleanly as stateless apps.
</Step>

<Step>
**What is a canary deployment?**

A canary releases the new version to a **small slice of real traffic** first (e.g., 5%), watches its metrics, and expands only while the numbers hold:

```
v1.4: 95% | v1.5: 5% → error rate OK? → 25% → 50% → 100%
```

The defining feature vs blue-green: promotion is decided by **metrics**, so a bad release is caught automatically after touching only 5% of users. Compare all three strategies in one line: rolling (gradual, capacity-efficient), blue-green (atomic switch, instant rollback), canary (smallest blast radius, needs metric analysis).
</Step>
</Steps>
