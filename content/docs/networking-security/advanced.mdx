# Advanced Level

This section covers expert-level networking and security concepts commonly asked in interviews for senior professionals.

<Steps>
<Step>
**What is mutual TLS (mTLS), and how does it work in a service mesh?**

Standard TLS authenticates only the server; **mTLS authenticates both sides** — each service presents a certificate the other verifies before any application data flows:

- **How it works** — both parties exchange certificates signed by a trusted internal CA, verify chains and identities, then establish the encrypted session
- **In Kubernetes** — a mesh (Istio/Linkerd) automates everything: sidecars terminate mTLS, certificates are short-lived and auto-rotated (SPIFFE-style workload identities like `spiffe://prod/ns/payments/sa/checkout`), and AuthorizationPolicies grant access by that identity — "the payments service may call orders:8080", not by IP
- **Why it matters** — zero-trust east-west traffic: a compromised pod can't impersonate others, sniff traffic, or reach services its identity isn't authorized for
- **The operational costs to acknowledge** — CA/certificate lifecycle management, mesh control-plane operations, and debugging encrypted traffic (mesh observability replaces packet captures)

The implementation sequence interviewers respect: observability-only mode → PERMISSIVE mTLS (accept both) → STRICT (reject non-mTLS) — with per-namespace rollout.
</Step>

<Step>
**What is a SIEM, and how does it fit into a DevOps-managed environment?**

A SIEM (Splunk, Elastic Security, Sentinel, Chronicle) aggregates security telemetry from across the estate — logs, cloud audit trails, network flows, endpoint data — normalizes it, and provides **detection, correlation, and incident workflow**:

- **What it detects** — correlated threats invisible in single sources: impossible-travel logins across services, anomalous API-call patterns, credential-stuffing campaigns, privilege-escalation sequences
- **Detection-as-code** — modern SIEM rules are versioned and deployed through pipelines like everything else (Sigma rules, Sentinel analytics rules)
- **The DevOps responsibilities** — ship the right telemetry (CloudTrail, audit logs, app security events) with consistent schemas; tune rules to reduce false positives; wire SIEM alerts into the same on-call and incident process as operational alerts
- **Compliance role** — the SIEM's immutable store and dashboards double as audit evidence

The insight to deliver: a SIEM fed by an unmanaged firehose produces noise, not security — log schema discipline and rule tuning are DevOps work, not just a SOC function.
</Step>

<Step>
**What is threat modeling, and how do you run one for a service?**

Threat modeling identifies what can go wrong *before* building — the cheapest security activity there is. The practical methods:

- **STRIDE** — categorize threats per component: **S**poofing, **T**ampering, **R**epudiation, **I**nformation disclosure, **D**enial of service, **E**levation of privilege
- **The process** — diagram the data flows (trust boundaries: internet→LB→service→DB) → enumerate threats per boundary using STRIDE → rate (DREAD or simple risk = likelihood × impact) → assign mitigations with owners
- **When** — design reviews for new services, major architecture changes, and feature additions touching auth/data

A worked example to have ready: *a new file-upload feature* — spoofing: unauthenticated uploads? tampering: content-type spoofing/malware? disclosure: public bucket URLs? DoS: unbounded file size? EoP: path traversal on file names? Each becomes a concrete control (auth, scanning, signed URLs, size limits, sanitized paths).

The integration with DevOps: threats become issues in the backlog and, where possible, policy-as-code gates — the model stays alive instead of dying in a design doc.
</Step>

<Step>
**Walk me through the OWASP Top 10 — what are the risks and their DevOps-relevant defenses?**

The current OWASP Top 10 (2021), with the controls that matter to platform engineers:

1. **Broken Access Control** — users act outside intended permissions → authorization tests in CI, deny-by-default, no IDOR-prone direct object references
2. **Cryptographic Failures** — weak/absent encryption of sensitive data → TLS everywhere, KMS-managed keys, no homemade crypto
3. **Injection** (SQL/command) — → parameterized queries, prepared statements; SAST scanning in the pipeline
4. **Insecure Design** — missing security at the architecture level → threat modeling, design reviews
5. **Security Misconfiguration** — the #1 cloud breach class → IaC scanning (Checkov/tfsec), policy-as-code, hardened defaults, no default credentials
6. **Vulnerable & Outdated Components** — → SCA scanning (Snyk/Dependabot), SBOMs, pinned dependencies
7. **Identification & Authentication Failures** — weak sessions/credentials → MFA, secure session handling, credential-stuffing protection
8. **Software & Data Integrity Failures** — untrusted updates/pipelines → signed artifacts, verified dependencies, SLSA-style pipeline integrity
9. **Security Logging & Monitoring Failures** — breaches undetected → the logging/alerting discipline from this whole section
10. **Server-Side Request Forgery (SSRF)** — server fetches attacker-chosen URLs → URL allowlists, no raw user URLs, metadata-endpoint blocks (see the SSRF question)

The framing to deliver: OWASP is a *prioritization* for application security work — and platform engineers implement the scanning, policy, and logging layers that catch these categories continuously.
</Step>

<Step>
**What is SSRF, and why does it matter so much in cloud environments?**

Server-Side Request Forgery tricks your server into making requests to attacker-chosen URLs — and in the cloud, the server's network position is the treasure:

- **The crown jewel** — cloud metadata endpoints: `http://169.254.169.254/latest/meta-data/iam/security-credentials/` returns the instance's IAM credentials. The 2019 Capital One breach (~100M records) was exactly this class
- **Classic entry points** — user-supplied URLs for "fetch this image"/"webhook back", PDF generators, URL previews
- **Defenses, layered**:
  - **Network** — IMDSv2 (token-based, session-required — blocks naive SSRF), deny egress to link-local/metadata ranges except from trusted services, segment so the fetching service can't reach internal APIs
  - **Application** — strict URL allowlists, resolve-and-validate the *IP* (block re-DNS tricks), no redirects followed to internal ranges, schema+port allowlists
  - ** blast-radius** — least-privilege instance roles: a compromised fetcher service holds no production credentials
</Step>

<Step>
**L3 vs L4 vs L7 firewalls — and where do WAF and security groups fit?**

- **L3 (network)** — filters by IP/subnet: "block this source range" (NACLs, route/firewall appliances)
- **L4 (transport)** — filters by port/protocol with connection state: "only 443 to this target, established connections only" (security groups, NLB, host firewalls)
- **L7 (application)** — inspects the protocol payload: HTTP methods, paths, headers, bodies (WAF, API gateway policies)
- **WAF** — the specialized L7 layer: managed attack signatures (SQLi/XSS), bot management, rate limiting per identity

The placement picture to draw: edge (CDN + WAF, L7) → perimeter (L4 security groups, only 443 open) → internal (segmented L3/L4 policies, mTLS between services). The follow-up to expect: *"why not just one L7 firewall everywhere?"* — L4 is far cheaper/faster, and defense-in-depth means each layer catches what the previous one misses.
</Step>

<Step>
**How does DNSSEC work, and why hasn't everyone adopted it?**

DNSSEC cryptographically signs DNS records so resolvers can verify they're authentic and unmodified — closing cache-poisoning and spoofing attacks:

- **The chain of trust** — root zone signs `.com`, `.com` signs `example.com`, `example.com` signs its records (RRSIG/DNSKEY/DS records); a validating resolver walks the chain
- **What it protects** — data integrity and origin authenticity between authoritative zone and validating resolver. **What it doesn't** — the last hop (stub→resolver) needs DoT/DoH; it doesn't encrypt (DNSSEC signs, doesn't hide), and it doesn't fix hijacked registrars
- **Operational costs (why adoption lags)** — key management with careful KSK/ZSK rollovers (a botched rollover makes the domain *unresolvable*), larger responses (fragmentation/amplification concerns), and every delegation in the chain must support it
- **The DevOps checklist** — sign your zones, automate rollover with monitoring, publish CAA/DS records in the registrar, alert on signature expiry (the classic DNSSEC outage: expired signatures)
</Step>

<Step>
**What is a Zero Trust network architecture, and how do you implement it?**

Zero Trust: **no implicit trust by network location** — every request is authenticated, authorized, and encrypted, regardless of source. The implementation pillars:

- **Identity everywhere** — strong authN for humans (SSO+MFA, phishing-resistant keys) and workloads (mTLS identities, SPIFFE); short-lived credentials, no standing access
- **Least-privilege authorization per request** — policy decisions on identity + context (device posture, sensitivity), not source IP
- **Segmentation to the workload** — default-deny everywhere (K8s NetworkPolicies, micro-segmentation), brokered access replacing VPN SSH (SSM Session Manager, BeyondCorp-style proxies)
- **Assume breach** — full audit trails, anomaly detection, and blast-radius limits (accounts, namespaces) so one compromise stays contained

The migration path interviewers want: it's incremental — (1) centralize identity + kill static credentials, (2) segment east-west, (3) broker all administrative access, (4) mTLS between services, (5) per-request authorization. Perimeter firewalls remain; they stop being *the* control.
</Step>

<Step>
**What is the difference between authentication and authorization, and where does each live?**

- **Authentication (AuthN)** — *who are you?* — verifying identity: passwords, MFA, certificates, OIDC ID tokens
- **Authorization (AuthZ)** — *what may you do?* — permissions checked per request: RBAC, ABAC, policy engines

Where each lives in a typical stack:

- **AuthN** — centralized at the IdP (SSO) for humans, workload identity (IAM/mTLS) for services — authenticate once, propagate identity as signed tokens (JWTs)
- **AuthZ** — layered: coarse-grained at the gateway (which routes may this identity touch?), fine-grained in the service (is this user allowed to edit *this* record?) — object-level decisions can't live in the gateway
- **Standards to name** — OAuth 2.0 scopes, JWT claims, OPA/ Cedar for externalized authorization decisions

The failure mode to articulate: conflating the two — "authenticated" ≠ "authorized" (a valid JWT for service A doesn't authorize service A to read user X's data) — which is exactly the Broken Access Control category of the OWASP Top 10.
</Step>

<Step>
**What is HSTS, CSP, and which security headers should every service set?**

HTTP response headers are cheap, high-value hardening — the set to standardize on every service (ideally enforced centrally at the ingress/gateway):

- **HSTS** (`Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`) — forces browsers to HTTPS, blocking downgrade/SSL-stripping attacks; submission to the preload list makes it apply before the first visit
- **CSP** (`Content-Security-Policy: default-src 'self'`) — restricts what scripts/resources a page may load — the strongest XSS mitigation; requires iteration with the frontend team
- **X-Content-Type-Options: nosniff** — blocks MIME-type sniffing
- **X-Frame-Options / CSP frame-ancestors** — prevents clickjacking via framing
- **Referrer-Policy, Permissions-Policy** — limit data leakage and feature access

The enforcement pattern: headers set centrally (ingress/gateway) with per-app overrides, validated by automated checks (security headers scanners in CI/E2E tests) — plus the server-side work headers remind you about (HTTPS-only cookies, `Secure`/`HttpOnly`/`SameSite` flags).
</Step>

<Step>
**How do you secure CI/CD pipelines themselves — the supply chain of your supply chain?**

The pipeline holds production credentials and injects code into production — securing it is its own discipline:

- **Identity** — OIDC federation (no static cloud keys), least-privilege per workflow, SSO+MFA for the CI platform itself
- **Untrusted code isolation** — fork PRs run on ephemeral, unprivileged runners with no secrets mounted; `pull_request_target` used with extreme care (it runs with secrets and checkout of the base branch)
- **Dependency integrity** — pin actions by SHA (not mutable tags), lockfiles committed, private registries, provenance attestations (SLSA levels)
- **Artifact integrity** — sign images/artifacts (cosign), verify signatures at deploy admission, SBOMs generated and stored
- **Change control** — protected branches, required reviews, no direct-to-main, audit logs of every workflow change (workflow definitions are code that runs with secrets)

The attack-path framing to close with: walk "attacker compromises X" for X = developer laptop, dependency, runner, or the CI config itself — and show a control per path. That's the senior-level answer.
</Step>

<Step>
**What is Kubernetes RBAC plus NetworkPolicy in practice — how do you secure a namespace end to end?**

Securing one namespace combines API-level and network-level controls:

- **RBAC** — a namespace-scoped Role with exactly the verbs needed (`get/list/watch` pods for a dashboard; `create/update` deployments for CI); dedicated ServiceAccounts per workload; `automountServiceAccountToken: false` when the API isn't needed; no ClusterRoleBindings for routine access
- **NetworkPolicy** — default-deny ingress+egress for the namespace, then explicit allows: frontend→api:8080, api→db:5432, everything→DNS:53; egress to external APIs via named ports/IP blocks
- **Pod hardening** — `runAsNonRoot`, `readOnlyRootFilesystem`, dropped capabilities, seccomp profile, no privileged pods (enforced by Pod Security Standards `restricted` or Kyverno policy)
- **Secrets** — vault-synced (External Secrets), not plaintext; RBAC limits who can read Secret objects
- **Verification** — `kubectl auth can-i --list` per identity, a policy-testing pod (can it reach the DB directly? it shouldn't), and admission policies (Kyverno/Gatekeeper) as the backstop

The summary line: RBAC controls *who talks to the API*, NetworkPolicy controls *who talks to whom on the network*, pod security contexts constrain *what a compromised container can do* — all three, or none of them is really in place.
</Step>

<Step>
**How do you respond to a security incident — what does the DevOps side of incident response look like?**

Security incidents add containment and forensics to the operational incident process:

- **Contain fast** — revoke credentials/sessions (the vault/KMS revocation path you tested), isolate affected hosts/pods (NetworkPolicy quarantine), block indicators at the WAF/firewall — containment actions you rehearsed
- **Preserve evidence** — snapshot instances/volumes before termination, retain logs (extend retention immediately — log rotation is the evidence-destroyer), record timelines
- **Eradicate & recover** — rotate *all* potentially exposed secrets (assume captured), patch the entry point, rebuild compromised hosts from known-good images (immutable infrastructure earns its keep here), verify with fresh scans before restoring traffic
- **Report** — regulatory clocks may apply (GDPR 72h notification), customer communications, post-mortem: entry point, dwell time, blast radius, and the control that would have caught it earlier
- **The DevOps-specific duties** — your IaC, pipelines, and secrets are both *targets* and *instruments*: pipeline compromise means treat all recent artifacts as suspect; audit logs answer "what did the attacker's credentials touch?"

The maturity line: the difference between a bad week and a catastrophe is rehearsed revocation, immutable infrastructure, and evidence-preserving defaults — all built before the incident.
</Step>
