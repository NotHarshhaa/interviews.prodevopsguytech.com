# Advanced Level

This section covers expert-level concepts in Infrastructure as Code, including CI/CD integration, security best practices, and enterprise-scale implementations.

## Terraform Questions

<Steps>
<Step>
**How do you implement CI/CD pipelines for Terraform?**

The standard pattern is **plan on PR, apply on merge** — with the plan as the review artifact:

```yaml
# GitHub Actions (current action versions)
jobs:
  terraform:
    runs-on: ubuntu-latest
    permissions:
      id-token: write        # OIDC: short-lived cloud credentials, no stored keys
      contents: read
      pull-requests: write   # post the plan as a PR comment
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform fmt -check && terraform validate
      - run: terraform plan -out=tfplan
      - name: Post plan to PR
        uses: hashicorp/setup-terraform@v3 # or actions/github-script, to render the plan
      - name: Apply (main branch only)
        if: github.ref == 'refs/heads/main' && github.event_name == 'push'
        run: terraform apply -auto-approve tfplan
```

Elements that make it production-grade:

- **Plan-as-comment** — reviewers see the exact create/update/destroy diff in the PR
- **State locking via backend** — concurrent plans are safe, applies serialize
- **OIDC federation** — no static cloud keys in CI
- **Policy gates** — OPA/Sentinel/Checkov evaluate the plan before apply
- **Manual approval for prod** — GitHub Environments / GitLab protected environments
- Tools worth naming: Atlantis (PR-driven plans/applies), Terraform Cloud/Enterprise run pipelines, Digger
</Step>

<Step>
**What is policy-as-code for Terraform, and which tools exist?**

Policies evaluate the **plan output** and reject infrastructure that violates org standards — before any resource is created:

- **Sentinel** — HashiCorp's framework (Terraform Cloud/Enterprise); HCL-like policies with `tfplan`/`tfconfig` imports, soft-mandatory vs hard-mandatory enforcement
- **OPA / Conftest** — Rego policies against plan JSON; free and cloud-neutral
- **Checkov / tfsec** — security-focused scanners (CIS benchmarks, encryption, public access) run directly on the code

```python
# Sentinel: deny unencrypted S3 buckets
import "tfplan"
main = rule {
  all tfplan.resources.aws_s3_bucket as _, bucket {
    bucket.provides["server_side_encryption_configuration"] is not null
  }
}
```

The lifecycle to describe: policies versioned in Git, tested like code, rolled out in **advisory mode first** (violations warn), then enforced — and every exception is documented with an expiry.
</Step>

<Step>
**How do you detect and manage infrastructure drift?**

Drift = live infrastructure diverging from state + code — from console changes, out-of-band hotfixes, or broken automation:

- **Detect** — scheduled `terraform plan` runs (zero diff = clean); Terraform Cloud drift detection; S3 backend resources flagged by external tools (driftctl — now Snyk IaC)
- **Decide the policy per resource** — GitOps-style **auto-revert** (drift is undone) for standard resources vs **alert-and-review** for the few that legitimately change outside Terraform (autoscaling, some tags)
- **The import rescue** — a manually created emergency resource gets `import`-ed into state and codified immediately, so it's not the next untracked snowflake
- **Prevention** — IAM without console write access to prod, IaC-only change policy, and making the pipeline path *faster* than the console

The consequence to articulate: drift means the next `terraform apply` may **revert a live fix** — that's why detection is scheduled, not done "when we remember".
</Step>

<Step>
**How do you manage multi-region and multi-account Terraform at scale?**

- **Multi-region** — aliased providers let one configuration manage several regions:

```hcl
provider "aws" {
  alias  = "primary"
  region = "us-east-1"
}
provider "aws" {
  alias  = "dr"
  region = "eu-west-1"
}

resource "aws_s3_bucket" "replica" {
  provider = aws.dr      # this resource lives in the DR region
}
```

- **Multi-account** — one Terraform "landing zone": account/OU structure via AWS Organizations, role assumption across accounts (`assume_role` in the provider), and separate state per account/env — blast-radius isolation
- **Scale structure** — directory-per-environment or per-stack repos, shared versioned modules, Terragrunt (or Terramate) to de-duplicate backend/config boilerplate across hundreds of stacks
- **OpenTofu** — the open-source Terraform fork worth naming for vendor-independence discussions (drop-in compatible, Linux Foundation governed)

The scaling principle: many small states beat one giant state — plan/apply speed, lock contention, and blast radius all improve per stack.
</Step>

<Step>
**Terraform Cloud/Enterprise vs open-source Terraform — what do you get?**

- **Remote runs** — plan/apply executed on managed workers; state locking, drift detection, and scheduled runs built in
- **Private module registry** — org-wide, versioned module sharing with usage visibility
- **Sentinel/OPA policy enforcement** — policy-as-code applied to every run
- **Team governance** — RBAC per workspace, audit logs, SSO
- **Cost estimation** — pre-apply cloud cost estimates per plan

The comparison answer: OSS Terraform + CI (Atlantis/GitHub Actions) + DIY state management gets you surprisingly far — TFC/Enterprise buys the *operational* layers (governance, drift, registry, agent isolation) that large orgs otherwise hand-build. Also know HCP Terraform as the current branding and the OSS OpenTofu alternative.
</Step>

<Step>
**How do you test Terraform code?**

Layered like any other code:

- **Static** — `terraform fmt -check`, `terraform validate`, `tflint` (provider-aware linting: invalid instance types, deprecated syntax)
- **Security** — Checkov/tfsec/Trivy on the code (public buckets, open SGs, unencrypted volumes)
- **Policy** — OPA/Sentinel on the plan JSON
- **Integration** — **Terratest** (Go): deploys real infrastructure into a disposable account, asserts behavior (endpoint responds, bucket refuses public access), then destroys
- **Smoke after apply** — pipeline post-apply checks against the created resources

```go
// Terratest sketch
terraformOptions := &terraform.Options{ TerraformDir: "../examples/simple" }
defer terraform.Destroy(t, terraformOptions)
terraform.InitAndApply(t, terraformOptions)
assert.Equal(t, "t3.micro", terraform.Output(t, terraformOptions, "instance_type"))
```

The tiering to state: every PR gets static + security + plan review; integration tests run nightly or per-release (they cost real cloud money); prod applies are gated by all of the above.
</Step>
</Steps>

## Ansible Questions

<Steps>
<Step>
**How do you implement RBAC in Ansible Automation Platform (Tower/AAP)?**

Ansible Automation Platform gives Ansible a web UI, scheduling, and enterprise access control:

- **Organizations → Teams** — the hierarchy: users belong to teams, teams belong to organizations
- **RBAC by object** — permissions attach to job templates, inventories, projects, and credentials (use/read/execute/admin), so a team can *run* a deploy job without seeing the credentials inside it
- **Credential isolation** — machine credentials, vault credentials, and cloud credentials are stored encrypted; users reference them, never view them
- **Execution environments** — containerized runner images with pinned Ansible/tool versions, per-job isolation

The enterprise pattern: git-backed projects (playbooks pulled from Git), scheduled/triggered job templates, and RBAC such that developers execute a "deploy" button without raw SSH access to any host.
</Step>

<Step>
**How do you handle secrets in Ansible at scale?**

- **Ansible Vault** — encrypt files or single values (`ansible-vault encrypt_string`); vault passwords via prompt, password file (mode 600), or CI-injected; use **multiple vault IDs** for per-environment keys
- **HashiCorp Vault lookup** — `lookup('community.hashi_vault.vault_read', ...)` fetches secrets at runtime instead of storing them — combined with short-lived dynamic credentials (Vault's database engine), this is the scale answer
- **Cloud secret stores** — AWS Secrets Manager lookup plugins; secrets pulled per task, never written to disk
- **The rules that hold everywhere** — no plaintext secrets in playbooks or Git, `no_log: true` on tasks handling sensitive output, and rotation that doesn't require re-encrypting every playbook

The scale insight: Vault-style dynamic secrets change the failure model — a leaked credential expires on its own, and revocation is immediate from the vault.
</Step>

<Step>
**How do you write a custom Ansible module?**

When no module fits, write one in Python following the module contract — **idempotent, JSON-in/JSON-out**:

```python
#!/usr/bin/python
from ansible.module_utils.basic import AnsibleModule

def main():
    module = AnsibleModule(
        argument_spec=dict(
            name=dict(required=True, type='str'),
            state=dict(default='present', choices=['present', 'absent']),
        ),
        supports_check_mode=True,
    )

    name = module.params['name']
    current = get_current_state(name)          # read actual state
    desired = module.params['state']

    if module.check_mode:                      # honor --check
        module.exit_json(changed=(current != desired))

    if current != desired:
        apply_change(name, desired)            # perform the change
        module.exit_json(changed=True, name=name)
    module.exit_json(changed=False, name=name)

if __name__ == '__main__':
    main()
```

- **Contract details** — `argument_spec` validates inputs; `supports_check_mode` honors dry runs; `exit_json(changed=...)` reports idempotency; failures via `fail_json(msg=...)`
- **Before writing one** — check whether a `script` task, `command` with `creates:`, or an existing collection module suffices; custom modules carry maintenance cost
- **Distribution** — bundle into a collection with docs and tests
</Step>
</Steps>

## CloudFormation Questions

<Steps>
<Step>
**How do you implement cross-stack references in CloudFormation?**

Export outputs from one stack; import them into another:

```yaml
# Network stack — export
Outputs:
  VpcId:
    Value: !Ref MyVPC
    Export:
      Name: prod-vpc-id
---
# App stack — import
Resources:
  AppSubnet:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !ImportValue prod-vpc-id
```

- **The constraint to know** — you **cannot delete a stack (or a resource) while its exports are imported elsewhere** — CloudFormation enforces the dependency graph across stacks
- **Naming discipline** — stable export names (`<env>-vpc-id`); renaming breaks every consumer
- **Alternatives at scale** — SSM Parameter Store (more flexible than exports, but loses the delete-protection), or nested stacks/one-big-stack when everything is one lifecycle. AWS-native answer for org-wide sharing: Resource Access Manager for subnets/transit gateways
</Step>

<Step>
**How do rollbacks and drift detection work in CloudFormation?**

- **Automatic rollback** — a failed create/update reverts the stack to the previous stable template; failure details land in stack events. **RollbackConfiguration** adds monitoring alarms that trigger rollback when the *application* misbehaves post-update (runtime failures, not just deploy failures)
- **Continue/fix flows** — `--disable-rollback` for debugging failed creates; `continue-update-rollback` after fixing the cause of a failed update-rollback
- **Drift detection** — `aws cloudformation detect-stack-drift` compares live resources against the template: statuses IN_SYNC / MODIFIED / DELETED per resource. Console changes become visible — the same problem Terraform drift solves, with the same remedy (re-codify or revert)
- **Update policies** — `UpdateReplacePolicy`/`DeletionPolicy: Retain` protect stateful resources during replacements and stack deletion

The expert framing: rollback alarms (app health) + drift detection + Retain policies together make CloudFormation stacks safe to hand to CI/CD.
</Step>

<Step>
**What are Lambda-backed custom resources, and when do you use them?**

When CloudFormation has no native resource type for something you need, a **custom resource** delegates creation/update/delete to a Lambda:

```yaml
Resources:
  MyCustom:
    Type: Custom::SshPublicKey
    Properties:
      ServiceToken: !GetAtt CustomHandler.Arn    # the Lambda's ARN
      KeyName: deploy-key

  CustomHandler:
    Type: AWS::Lambda::Function
    Properties:
      Runtime: python3.12
      Handler: index.handler
      Code: ...
```

The Lambda receives the request type (Create/Update/Delete) plus `ResourceProperties`, performs the action, and **must respond** to the pre-signed SNS/queue URL — a hung handler blocks the stack for an hour.

- **When to use** — third-party APIs not yet in CloudFormation, data migrations at deploy time, custom validations
- **The modern alternative to lead with** — **CloudFormation Registry resource types** (CFN-CLI to develop first-class typed resources) and, honestly, Terraform for resources CloudFormation lacks
- **The gotchas** — idempotent handlers, correct response on every path (including errors — otherwise stack timeouts), and Delete handling that doesn't leak the external resource
</Step>

<Step>
**How do you deploy across multiple accounts with StackSets?**

StackSets deploy one template to many accounts/regions in one operation — the mechanism behind org-wide baselines:

```yaml
Type: AWS::CloudFormation::StackSet
Properties:
  TemplateURL: s3://org-templates/baseline.yaml
  PermissionModel: SERVICE_MANAGED        # via AWS Organizations
  AutoDeployment:
    Enabled: true                          # new accounts inherit automatically
    RetainStacksOnAccountRemoval: false
  Capabilities: [CAPABILITY_NAMED_IAM]
```

- **Permission models** — SERVICE_MANAGED (Organizations-managed, auto-deployment for new accounts) or SELF_MANAGED (cross-account IAM roles you provision)
- **Deployment targets** — OUs or account lists, per-region deployment ordering, **account-level stack instances** with per-instance parameter overrides
- **The guardrail pattern it enables** — org-wide security baselines (CloudTrail everywhere, mandatory encryption, guardduty) deployed and *kept deployed* by the StackSet — new accounts are compliant on creation
- **Alternatives worth naming** — Control Tower built on StackSets, Terraform for org-level management when you're multi-cloud
</Step>

<Step>
**How do you test infrastructure code — Terraform and CloudFormation — in CI?**

Layered testing, mirroring application code:

- **Static** — `terraform fmt/validate`, tflint; CloudFormation: `cfn-lint` (syntax, property validation), cfn-nag (security)
- **Security scanning** — Checkov/tfsec (IaC misconfigs: open SGs, unencrypted storage, public access) as PR gates
- **Plan/change-set review** — the diff posted to the PR; policy-as-code (OPA/Sentinel) evaluating the plan
- **Integration tests** — **Terratest** for Terraform (deploy to a disposable account, assert behavior, destroy); CloudFormation: deploy to a test account + assertion scripts (or pytest with boto3) + teardown
- **Post-deploy smoke** — pipeline asserts the created endpoints/buckets behave as declared

The budget note to include: integration tests spend real money and take real time — run static/security on every PR, integration nightly or per-release against ephemeral accounts, and keep destroy-after-test non-negotiable.
</Step>
</Steps>
