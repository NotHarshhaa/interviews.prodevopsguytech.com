# Beginner Level

This section covers fundamental concepts of cloud computing, including basic principles, services, and common practices.

<Steps>
<Step>
**What is cloud computing?**

Cloud computing is the on-demand delivery of computing resources — servers, storage, databases, networking, software — over the internet, with **pay-as-you-go** billing instead of upfront hardware purchases.

The defining characteristics (per NIST): **self-service** (provision in minutes from a console/API), **elasticity** (scale with demand), and **measured usage** (you pay for what you consume). For DevOps specifically, the cloud turned "waiting three weeks for a server" into "running a pipeline that provisions one in three minutes" — which is why IaC and cloud grew up together.
</Step>

<Step>
**What are the different types of cloud computing?**

By **deployment model**:

- **Public cloud** — provider-operated infrastructure shared across customers (AWS, Azure, GCP); you get scale and zero hardware ownership
- **Private cloud** — dedicated infrastructure for one organization (on-prem VMware/OpenStack or a provider's dedicated tenancy); control and compliance, at the cost of owning capacity
- **Hybrid cloud** — the two connected as one estate; the realistic default for enterprises with existing data centers, regulated workloads, or migration timelines

(Hybrid is the model to understand well — "cloud vs on-prem" is a false choice in most real organizations.)
</Step>

<Step>
**What are the benefits of cloud computing?**

- **Elasticity** — scale up for a traffic spike, scale down the same afternoon; capacity follows demand
- **Cost model shift** — CapEx (buying hardware) becomes OpEx (paying for usage); no paying for idle servers "just in case"
- **Speed** — infrastructure provisions in minutes via API, enabling experimentation and fast failure
- **Global reach in minutes** — deploy to any region without building a data center there
- **Managed services** — databases, queues, ML platforms: you operate less undifferentiated heavy lifting
- **Disaster recovery** — multi-AZ/region replication that would be unaffordable to build yourself

Worth naming the honest trade-offs: egress costs, regional outages do happen, and without governance the same speed produces runaway spend.
</Step>

<Step>
**What are the main cloud service models (IaaS, PaaS, SaaS)?**

The models differ in **who manages what** — the classic "pizza analogy" (made at home / delivered / eaten at a restaurant):

- **IaaS** — you manage OS, runtime, and app; provider manages hardware, network, virtualization. *Examples:* EC2, Azure VMs, GCE. Maximum control, most operational work
- **PaaS** — you manage only your code and data; provider runs the runtime and scaling. *Examples:* Elastic Beanstalk, App Engine, Heroku, Azure App Service
- **SaaS** — complete applications you just use. *Examples:* Gmail, Salesforce, Office 365

The DevOps angle: modern architectures mix all three (VMs/containers for core systems, managed services for databases/queues, SaaS for tooling) — knowing what each model takes off your plate is the real interview skill.
</Step>

<Step>
**What is serverless computing?**

Serverless lets you run code without provisioning or managing servers — the provider handles capacity, scaling, and patching. *Examples:* AWS Lambda, Azure Functions, Google Cloud Functions/Run, and managed services like DynamoDB.

Characteristics that matter:

- **Event-driven** — a function runs in response to a trigger (HTTP request, file upload, queue message)
- **Per-invocation billing** — no cost while idle
- **Automatic scaling** — from zero to thousands of concurrent executions
- **Constraints** — execution time limits, cold starts, and no long-lived local state

Use it for spiky, event-driven, short-lived workloads (glue, APIs with variable traffic, stream processing) — not for long-running, latency-critical, or constant-load services.
</Step>

<Step>
**What is virtualization, and how does it differ from containers?**

Virtualization lets one physical server run many isolated **virtual machines** via a **hypervisor** (VMware ESXi, KVM, Hyper-V) — each VM gets virtual hardware and a full guest OS.

The comparison interviewers want:

- **VMs** — heavy (each carries a full OS, GBs), slower to boot, but fully isolated with any OS
- **Containers** — lightweight (share the host kernel, MBs), start in seconds, ideal for CI/CD artifact-style deployments — but isolated less strongly than VMs and tied to the host OS family

Clouds combine both: the provider's physical hosts run VMs (that's your EC2 instance), and your containers run inside those VMs — hardware isolation below, fast packaging above.
</Step>

<Step>
**What is multi-cloud?**

Multi-cloud means using two or more providers (AWS + Azure + GCP) — usually by *distributing different workloads* per provider rather than duplicating one app everywhere.

Motivations: best-of-breed services, existing acquisitions/infrastructure, negotiating leverage, and (sometimes) resilience against a provider outage. The honest trade-off to state: each additional cloud multiplies operational surface — separate IAM, networking, billing, and security models — so portable building blocks (Kubernetes, Terraform, Vault) are what keep it manageable. Multi-cloud is a strategy, not a default.
</Step>

<Step>
**What is the difference between elasticity and scalability?**

- **Scalability** — the *capability* to handle growth: the architecture can serve more load (by adding resources)
- **Elasticity** — the *automation* of that capability in both directions: resources are added **and removed automatically** to match demand, so you pay for what you use

A system can be scalable but not elastic (you can add servers, but someone must provision them manually). Cloud elasticity is what makes "scale to zero overnight, handle Black Friday at noon" possible. Related term: **auto-scaling** is the mechanism that delivers elasticity.
</Step>

<Step>
**What is an Availability Zone (AZ), and how does it differ from a region?**

- **Region** — a geographic location containing multiple physically separated data centers (e.g., `us-east-1`, `westeurope`)
- **Availability Zone** — one or more data centers *within* a region, with independent power/cooling/networking, connected by low-latency links (`us-east-1a`, `us-east-1b`, ...)

The design rule that follows: deploy across **multiple AZs** to survive a data-center failure (this is cheap — same region, low latency), and across **regions** to survive a regional failure (expensive — data replication, latency). Choosing a region itself is driven by latency to users, data-residency/compliance law, service availability, and pricing.
</Step>

<Step>
**What is the Shared Responsibility Model in cloud security?**

Security duties are split between provider and customer — and the split **shifts with the service model**:

- **Provider always handles** — physical security, hardware, hypervisor, network fabric
- **Customer always handles** — data, IAM/access decisions, application code, configuration
- **The shifting part** — in IaaS you patch the OS; in PaaS/serverless the provider does, but *your* dependencies and code remain yours

The interview trap this question tests: "the cloud is secure by default" is false. The major cloud breaches are customer-side misconfigurations (public S3 buckets, over-permissive IAM, leaked keys) — the provider's layer was fine.
</Step>

<Step>
**What is a Virtual Private Cloud (VPC)?**

A VPC is your own private, logically isolated network inside a public cloud — you define the address space and everything about how traffic flows:

- **Subnets** — segmented ranges, typically **public** (internet-routable) vs **private** (no direct internet access; databases, internal services)
- **Route tables** — where traffic goes (internet gateway, NAT gateway, VPC peering)
- **Security groups / network ACLs** — stateful instance-level and stateless subnet-level firewalls

The default architecture to describe: public subnets for load balancers only, private subnets for application and data tiers, NAT gateway for outbound-only internet access from private subnets, everything flowing through security groups with least privilege.
</Step>

<Step>
**What is a load balancer, and which types exist?**

A load balancer distributes incoming traffic across multiple healthy targets, giving you high availability and horizontal scaling in one component:

- **Layer 4 (network/TCP)** — routes by IP/port; extremely fast, protocol-agnostic (AWS NLB)
- **Layer 7 (application/HTTP)** — routes by URL path, headers, cookies; can terminate TLS, add health-based routing (AWS ALB, Azure App Gateway)
- **Global** — DNS-level routing across regions (Route 53, Cloud Load Balancing) for geo-failover

Key features to mention: **health checks** (unhealthy targets stop receiving traffic — this is what makes rolling deployments and failover work) and **cross-AZ distribution** so one AZ failing doesn't take the service down.
</Step>

<Step>
**What is object storage, and how is it different from block storage?**

- **Object storage** (S3, Azure Blob, GCS) — data stored as objects with metadata, addressed by unique keys in a flat namespace. Effectively unlimited capacity, extremely durable (S3 advertises 99.999999999% durability), accessed over HTTP/APIs. Perfect for files, backups, images, data lakes; useless for boot disks or databases that need random writes
- **Block storage** (EBS, Azure Managed Disks) — raw disk volumes split into fixed-size blocks, attached to one VM at a time. This is what databases and operating systems run on — low-latency random read/write
- **File storage** (EFS, Azure Files) — shared POSIX-style filesystems, many clients mounting simultaneously

Quick chooser: database → block; app static assets/backups/data lake → object; shared network filesystem → file.
</Step>

<Step>
**What is a CDN, and why does it matter?**

A Content Delivery Network (CloudFront, Cloudflare, Azure Front Door) caches content at edge locations around the world, serving users from the nearest point of presence instead of your origin:

- **Performance** — latency drops because the user's round trip is short; static assets, video, and API responses are served from cache
- **Origin offload** — the majority of requests never reach your servers (often 80–95% cache-hit for static-heavy sites), cutting both load and cost
- **Security** — CDNs absorb volumetric attacks and DDoS traffic before it touches your infrastructure, and terminate TLS at the edge

For DevOps, CDNs also change deployment math: cache invalidation/TTL strategy becomes part of the release plan (stale-cache bugs are a classic release-week incident).
</Step>

<Step>
**What is an IAM role, and how is it different from an IAM user?**

- **IAM user** — a long-lived identity with permanent credentials (password/access keys) attached to it
- **IAM role** — a set of permissions that is **assumed temporarily**: services, users, or federated identities take on the role and receive short-lived credentials automatically

Roles matter because they eliminate stored credentials:

```
EC2 instance → instance profile role → reads S3 bucket
Lambda function → execution role → writes to DynamoDB
CI pipeline → assumed role → deploys (no static AWS keys anywhere)
```

Best practice: humans federate through an identity provider into roles, services use roles, and IAM users with static keys exist only for break-glass scenarios. This is the foundation of "no long-lived credentials" security.
</Step>

<Step>
**What is AWS CloudFormation, and how does it compare to Terraform?**

CloudFormation is AWS's native Infrastructure-as-Code service: you declare resources in YAML/JSON templates, and it provisions and manages them as a **stack** with change sets (preview), drift detection, and rollback built in.

- **CloudFormation strengths** — deep, immediate AWS integration; managed state (no state files to babysit); free (you pay for resources, not the tool)
- **Terraform strengths** — **multi-cloud** (one workflow for AWS, Azure, GCP, and everything else), a larger provider ecosystem, HCL that many teams find more readable, and plan/apply workflow outside any one vendor
- **The practical answer** — AWS-only shops happily use CloudFormation; multi-cloud shops standardize on Terraform; both beat console-clicking. The concepts (declarative state, plan/preview, drift) transfer directly
</Step>

<Step>
**What is Google Kubernetes Engine (GKE)?**

GKE is Google Cloud's managed Kubernetes service — Google runs the control plane (API server, etcd, scheduling internals) while you manage worker nodes and workloads.

It's worth knowing as the benchmark for managed Kubernetes:

- **Autopilot mode** — GKE's standout feature: you deploy pods, and Google provisions and bills the nodes underneath — close to PaaS for Kubernetes
- **Origin advantage** — Kubernetes came from Google (Borg), so GKE typically ships new Kubernetes features first and handles upgrades well
- **Comparison frame** — AWS EKS and Azure AKS are the equivalents; the interview question is usually about *differences in control-plane management, node groups, and pricing* rather than core Kubernetes behavior, which is identical
</Step>

<Step>
**What is Azure DevOps?**

Azure DevOps is Microsoft's suite of development and delivery tools — five services under one roof:

- **Boards** — agile work tracking (kanban, sprints)
- **Repos** — Git hosting with pull requests
- **Pipelines** — CI/CD (the piece DevOps interviews focus on), with YAML pipelines, self-hosted agents, and strong multi-cloud deployment support
- **Artifacts** — package feeds (npm, NuGet, Maven, PyPI)
- **Test Plans** — manual and exploratory testing

Comparison frame: it competes with GitHub (which Microsoft also owns — GitHub Actions + Issues + Packages is the equivalent set). Many enterprises run Azure DevOps for Pipelines/Boards while code lives in GitHub — integration between the two is common and worth acknowledging.
</Step>

<Step>
**What is auto-scaling, and what are its key components?**

Auto-scaling automatically adjusts capacity to match demand — adding instances as load rises, removing them as it falls:

- **Trigger/metric** — what to watch: CPU, request count, queue depth, or a schedule (predictable daily peaks)
- **Bounds** — minimum and maximum instance counts (the cost and capacity guardrails)
- **Cooldown/stabilization** — wait periods that prevent thrashing (scaling events too close together)
- **Scale-in protection** — don't terminate an instance mid-task (classic with queue workers)

Example: an AWS Auto Scaling Group adds an instance when average CPU exceeds 70% for 5 minutes, caps at 20 instances, and drains queue workers gracefully before terminating them. In Kubernetes, the Horizontal Pod Autoscaler is the equivalent — same concepts, pod granularity.
</Step>
</Steps>
