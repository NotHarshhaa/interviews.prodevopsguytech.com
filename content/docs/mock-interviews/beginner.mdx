# Beginner Level

Practice these like a real interview: read the question, **answer it out loud first**, then compare with the model answer. Each entry includes the follow-ups you should expect and the trap most candidates fall into.

> **How to practice:** cover the answer → answer aloud in 60–90 seconds → compare → note what you missed. Interviewers grade structure and clarity as much as facts.

<Steps>
<Step>
**What is DevOps?**

**Model answer:** "DevOps is a set of practices and a culture that combines development and operations to deliver software faster and more reliably. The practices are things like CI/CD, infrastructure as code, and monitoring; the culture is shared ownership — the team that builds a service also runs it. The end goal is shortening the loop between writing code and running it safely in production."

**Follow-ups you should expect:**
- "What problems does DevOps actually solve?" — silos, slow manual releases, late feedback
- "Is DevOps a role or a culture?" — both exist; the culture is the point, the role enables it
- "How would you know a DevOps transformation is working?" — deployment frequency up, change failure rate down

**Common pitfall:** answering with a tool list ("Docker, Jenkins, Kubernetes…"). Tools implement DevOps; they aren't DevOps.
</Step>

<Step>
**Explain CI/CD.**

**Model answer:** "CI is developers merging small changes into a shared branch frequently, with every merge automatically built and tested — so integration problems surface in minutes. CD continues that automation toward production: *Continuous Delivery* means every change is automatically prepared and staged, with a human approving the final release; *Continuous Deployment* removes that gate, so every green change ships automatically."

**Follow-ups you should expect:**
- "What makes a good CI pipeline?" — fast (minutes), deterministic, fails loudly, gates merges
- "What runs in your pipeline before production?" — build, unit/integration tests, security scans, artifact packaging
- "Why does frequency matter?" — small batches = small blast radius and easy bisection

**Common pitfall:** stopping at "it automates deployments" — the interviewer is probing whether you understand *why* small, verified changes reduce risk.
</Step>

<Step>
**What is the difference between Continuous Delivery and Continuous Deployment?**

**Model answer:** "They're identical until the last step. Continuous Delivery automates everything up to a production-ready release and then requires human approval; Continuous Deployment automates that final push too. You pick delivery when releases need business or compliance sign-off, and deployment when your tests, monitoring, and rollback safety nets are trusted enough."

**Follow-ups you should expect:**
- "Which does your current team practice?" — have a real answer with a reason
- "What would you need in place to go from delivery to deployment?" — mature test coverage, canary/rollback automation, observability

**Common pitfall:** treating them as synonyms or arguing one is "more correct" — the difference is a deliberate, contextual choice.
</Step>

<Step>
**What is Infrastructure as Code, and what problem does it solve?**

**Model answer:** "IaC manages infrastructure — servers, networks, databases — through versioned definition files instead of console clicks. Tools like Terraform declare the desired state, plan the diff against reality, and apply it. The problems it solves: manual environments drift apart, changes aren't reviewable, recovery means rebuilding from memory. With IaC, infrastructure changes get the same review, history, and rollback as application code."

**Follow-ups you should expect:**
- "What's in the state file, and where does it live?" — remote backend, locking, never in Git
- "What's drift?" — reality diverging from code; detected by scheduled plans, fixed by re-codifying or reverting

**Common pitfall:** saying "it automates provisioning" and stopping — the reviewer/reproducibility/rollback properties are what the interviewer wants to hear.
</Step>

<Step>
**Why is version control important in DevOps?**

**Model answer:** "Git is the source of truth for everything in the system — application code, pipeline definitions, infrastructure code. It gives us review through pull requests, history and audit for every change, branching for parallel work, and `git revert` as often the fastest rollback. In DevOps, version control extends beyond source code to the entire delivery system, which is the foundation GitOps builds on."

**Follow-ups you should expect:**
- "What's your branching strategy?" — short-lived branches/PR flow; be able to defend it
- "What should be in Git?" — pipelines, IaC, dashboards as code; not secrets

**Common pitfall:** answering only from a developer's perspective — the interviewer wants to hear infrastructure and pipelines in Git too.
</Step>

<Step>
**Explain the difference between Docker containers and virtual machines.**

**Model answer:** "A VM virtualizes hardware: each VM runs a full guest OS on a hypervisor — gigabytes, minutes to boot, strongest isolation. A container shares the host kernel and isolates processes with namespaces and cgroups — megabytes, seconds to start, high density. Containers give speed and reproducibility; VMs give stronger isolation. In practice they stack: cloud VMs run containers inside them."

**Follow-ups you should expect:**
- "When would you still choose a VM?" — different OS needs, hard security boundaries, legacy software
- "What does 'share the kernel' imply for security?" — weaker boundary; hardening and sandboxing (gVisor/Kata) for untrusted workloads

**Common pitfall:** saying containers are "lighter VMs" without explaining *why* (kernel sharing) — the why is the interview.
</Step>

<Step>
**What is a Dockerfile, and walk me through building an image.**

**Model answer:** "A Dockerfile is the build recipe: `FROM` picks the base image, `COPY` adds files, `RUN` executes build-time commands, `CMD` sets the startup command. `docker build -t myapp:1.0 .` turns it into an image, where each instruction creates a cached layer. `docker run` starts a container from that image with a writable layer on top."

**Follow-ups you should expect:**
- "Why does instruction order matter?" — layer caching: copy dependency manifests before source so rebuilds reuse the expensive layer
- "How do you keep images small?" — multi-stage builds, alpine/distroless bases, `.dockerignore`
- "How do you get a shell in a running container?" — `docker exec -it <name> sh`

**Common pitfall:** reciting instructions without explaining layers/caching — order is where real-world Docker skill shows.
</Step>

<Step>
**What is Kubernetes, and what does it actually do for you?**

**Model answer:** "Kubernetes orchestrates containers across a cluster of machines. You declare desired state — '3 replicas of this image, this much CPU' — and controllers make reality match it continuously. Concretely it gives me: self-healing (crashed containers restart, dead nodes' pods reschedule), rolling updates with health gates, service discovery and load balancing between pods, and declarative config/secret management. It's the difference between running containers on one host and running them across a data center."

**Follow-ups you should expect:**
- "What's a pod, a deployment, a service?" — smallest unit; the controller managing replicas; the stable network address over moving pods
- "How does a rolling update not break the service?" — readiness probes gate traffic; failing rollouts abort automatically

**Common pitfall:** defining Kubernetes by its dashboard or commands instead of the declarative-reconciliation model — that's the concept interviewers test.
</Step>

<Step>
**How do you monitor production systems?**

**Model answer:** "Three data types, three jobs. Metrics (Prometheus) for numeric health — alerting on user-facing symptoms like error rate and latency. Logs (ELK/Loki) for detail — the 'why' when something breaks. Traces for distributed systems — 'where' in the request chain. I'd standardize the four golden signals — latency, traffic, errors, saturation — dashboards per service, and alerts that are actionable: paging on symptoms a human must handle, everything else to dashboards."

**Follow-ups you should expect:**
- "What would you alert on for a web API?" — error rate, p95/p99 latency, availability vs SLO; not CPU
- "What is alert fatigue?" — paging on noise until on-call ignores pages; fix by alerting on symptoms with thresholds and grouping

**Common pitfall:** listing tools without the metrics-vs-logs-vs-traces structure — the structure is what they're testing.
</Step>

<Step>
**A deployment you made broke production. Walk me through what you do.**

**Model answer:** "First, stabilize: roll back to the last known-good version — or toggle the feature off if it's behind a flag — faster than debugging live. Second, verify recovery with metrics and health checks. Third, preserve evidence: logs and the failing artifact for analysis. Fourth, root-cause offline — what test would have caught this? Fifth, fix forward with that test added, and redeploy through the normal pipeline. Finally, a blameless write-up so the process improves."

**Follow-ups you should expect:**
- "When would you *not* roll back immediately?" — when rollback is impossible (irreversible schema change) or when a fix-forward is faster and equally safe
- "How do you prevent recurrence?" — the missing test/gate added to the pipeline, not just the code fix

**Common pitfall:** starting with "I would debug the issue" — mitigation before investigation is the senior instinct they're checking for.
</Step>

<Step>
**What are environment variables, and how do you manage configuration across environments?**

**Model answer:** "Environment variables externalize configuration — endpoints, feature settings, credentials — so the same artifact runs in dev, staging, and production with only config differing. Non-sensitive config lives in versioned config files or config services; secrets come from a secrets manager (Vault, AWS Secrets Manager) injected at runtime — never hardcoded or committed. The key principle: one immutable artifact promoted through environments, config applied at deploy time."

**Follow-ups you should expect:**
- "Where do secrets *not* belong?" — Git, images, CI logs; and a secret that touched history is compromised — rotate it
- "How do containers get config?" — env vars or mounted files from ConfigMaps/Secrets

**Common pitfall:** proposing env vars *for secrets* without mentioning a secrets store — that's the follow-up trap.
</Step>

<Step>
**What is a load balancer, and what happens when a backend behind it fails?**

**Model answer:** "A load balancer distributes traffic across healthy backends — Layer 4 routes by IP/port, Layer 7 understands HTTP and can route by path or host. Health checks are the key mechanism: the balancer probes each backend (HTTP endpoint, TCP connect) and removes failures from rotation automatically, so a dead instance stops receiving users without human action. That's also what makes rolling deployments safe — new instances get traffic only after passing health checks."

**Follow-ups you should expect:**
- "L4 vs L7 — when each?" — raw speed vs content-aware routing
- "What's session persistence and when do you need it?" — sticky routing for stateful legacy apps; better to externalize state

**Common pitfall:** forgetting health checks — they're the mechanism behind nearly every availability answer.
</Step>

<Step>
**What is GitOps?**

**Model answer:** "GitOps makes Git the source of truth for deployment: an in-cluster controller — Argo CD or Flux — continuously compares the live cluster against the declared manifests in Git and reconciles differences. Deployment becomes a commit: reviewed, revertible, audited. Manual changes get detected and corrected as drift, and CI never needs credentials to production — the cluster pulls."

**Follow-ups you should expect:**
- "How do you roll back?" — `git revert` and sync
- "How do secrets fit?" — SOPS/Sealed Secrets/External Secrets — plaintext in Git is the classic GitOps mistake

**Common pitfall:** defining GitOps as "keeping Terraform in Git" — the reconciliation controller and pull model are the distinguishing parts.
</Step>

<Step>
**What questions do you have for us? (the closer)**

This closing question tests curiosity and preparation. Good questions to actually ask:

- "How do releases work today — frequency, process, and what gates them?"
- "What does on-call look like, and how do incidents feed back into engineering work?"
- "What's the biggest friction between dev and ops here right now?"
- "How much of the infrastructure is managed as code, and who owns it?"

**Common pitfall:** "no questions" (reads as disinterest) or asking only about perks. One thoughtful question about their delivery process signals exactly the mindset they're hiring.
</Step>
</Steps>
